# 기술 기록 문체 기준

기술 기록은 결과 보고서보다 작업 일지에 가깝게 쓴다. 독자가 코드를 처음 보는 상황을 가정하되, 실제로 겪지 않은 고민이나 장애를 만들어내지 않는다.

## 참고한 글의 장점

다음 글에서 설명의 흐름과 솔직한 회고 방식을 참고한다. 문장과 코드, 수치는 복사하지 않는다.

- [렌더링 파이프라인 흐름](https://tobrother.tistory.com/146): 개념을 설명한 다음 프로그램의 실제 진입점과 렌더 순서를 따라간다.
- [NavMesh](https://tobrother.tistory.com/158): 자료구조, 탐색, 최적화를 하나의 동작 흐름으로 연결한다.
- [Behavior Tree](https://tobrother.tistory.com/164): 처음 선택한 구조가 왜 버거워졌는지 인정하고 새 구조의 단점도 함께 적는다.

## 우리 기록에 적용할 규칙

1. 한 글은 하나의 질문만 다룬다.
2. 당시 상태와 구현되지 않은 범위를 먼저 밝힌다.
3. 개념 설명은 해당 코드 조각을 이해하는 데 필요한 만큼만 쓴다.
4. 코드 전체를 붙이지 않고 경계와 데이터 흐름이 드러나는 부분만 인용한다.
5. 성능 수치는 실행 명령, 환경, seed, 원본 CSV·JSON 경로를 함께 적는다.
6. 선택한 방법의 장점과 비용, 남은 한계를 같은 비중으로 적는다.
7. 결론은 배운 점보다 다음 변경에서 실제로 달라질 행동을 적는다.
8. 지나친 격식, 기계적인 병렬 문장, 과장된 성장 표현을 피한다.

## 문서 순서

```text
상황
재현
관찰
가설과 비교한 대안
선택
구현
검증
남은 한계
```

측정 결과가 가설을 지지하지 않으면 그 사실을 그대로 기록하고 최적화 성공 사례로 분류하지 않는다.
