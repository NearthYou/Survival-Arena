# GPU timestamp 302개 누락을 측정 실패로 다룬 기준

## 상황

포워드 렌더러 최적화 전에 RTX 3050 Ti 기준을 고정했다. 캐릭터 24명, AI 100개, 정적 객체 1,000개와 동적 광원 32개를 준비 120프레임 뒤 600프레임 측정했다. GPU timestamp는 기다리지 않는 16슬롯 순환 풀이었다.

## 재현

commit `36163138`의 MSVC Release, 1920×1080, seed `20260823`에서 기본 runner를 실행했다. 렌더와 CPU 표본은 끝났지만 [첫 실패 원본](../../benchmarks/forward-baseline/20260823-032931-36163138-seed20260823/FAILED.md)은 GPU 표본 600개 중 302개가 비어 제외됐다.

## 관찰

처음 16개 뒤 빈 구간과 유효 구간이 반복됐다. 원인을 나누는 진단에서 120프레임은 시작 거부 17, 정상 해석 103, disjoint 0, 미해석 0이었다. GPU 주파수나 timeout이 아니라 결과 회수가 16슬롯보다 늦어 생긴 풀 포화였다.

## 가설과 비교한 대안

프레임마다 `GetData`를 기다리면 CPU 시간에 GPU 대기가 섞인다. 누락만 버리면 통계가 치우치고, 32나 64슬롯도 다른 드라이버에서 충분하다는 근거가 없다. 프레임 수만큼 슬롯을 만드는 대신 query 객체 수가 실행 길이에 비례하는 비용을 받아들였다.

## 선택

비동기 회수는 유지하고 한 실행의 측정 프레임 수를 query 풀의 경계로 삼았다. 과도한 객체 생성을 막기 위해 측정 구간 상한은 10,000프레임으로 두고, 공식 runner는 누락이 하나라도 있으면 성공 통계를 만들지 않게 했다. 이 결정은 [비동기 프레임 측정 ADR](../../adr/0002-asynchronous-frame-benchmark.md)에 고정했다.

## 구현

`GpuFrameTimer`는 슬롯 수만큼 query를 미리 만든다. 진행 중 완료된 결과만 읽고, 제출 뒤 한 번 flush해 최대 2초 동안 남은 값을 회수한다. WARP 회귀 테스트는 미해석 query 20개를 연속 제출해 모든 슬롯이 시작되는지 확인한다.

## 검증

수정 뒤 120프레임 진단은 시작 거부 0, 정상 해석 120이었다. 같은 RTX 조건의 [채택 원본](../../benchmarks/forward-baseline/20260823-033736-80988ef7-seed20260823/RESULT.md)은 GPU 표본 `600/600`, GPU P95 `3.885056ms`, 프레임당 `2,240 draw calls`를 기록했다. 실행 조건과 수정 순서는 [개발 기록](../../devlog/2026-08-23-forward-baseline.md)에서 원본까지 이어진다.

## 남은 한계

600프레임 렌더 기준선은 마지막 100프레임의 working set 증가가 작아졌다는 사실만 보여 주며 메모리 누수를 부정하지 않는다. 전투 로직, 서버 통신, UI, 그림자와 투명 패스도 이 실행에 없으므로 최종 게임 프레임 성능으로 확대하지 않는다.
