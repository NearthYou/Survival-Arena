# 포워드 기준선에서 GPU 시간 302개가 비었던 이유

## 상황

5주차 최적화에 들어가기 전에 포워드 렌더러의 현재 비용부터 고정하려고 했다. 장면은 캐릭터 24명, AI 100개, 정적 객체 1,000개, 동적 포인트 광원 32개로 정했다. 인스턴싱과 컬링은 아직 넣지 않았고 객체와 mesh part마다 `DrawIndexed`를 호출한다.

비교 조건이 흔들리지 않도록 배치와 색, 애니메이션 시작점은 seed `20260823`에서 만들었다. 카메라와 애니메이션 시간도 벽시계 대신 프레임 번호를 60Hz 시간으로 바꿔 사용했다.

## 재현

commit `361631386a5c33e3be90bb54fcb9adb8a216035c`에서 기본 runner를 실행했다.

```powershell
./scripts/run_benchmark.ps1
```

조건은 MSVC Release, 1920×1080, 준비 120프레임과 측정 600프레임이었다. 실제 adapter는 NVIDIA GeForce RTX 3050 Ti Laptop GPU였다.

## 관찰

클라이언트는 720프레임을 정상 종료했고 CPU 값도 600개 있었다. GPU 값은 298개뿐이었고 302개가 비었다. 처음 16개는 연속으로 채워졌지만 그 뒤로 빈 구간과 유효 구간이 주기적으로 반복됐다.

timestamp는 세 경우에 비게 돼 있었다. 빈 슬롯이 없어 query를 시작하지 못한 경우, `Disjoint`가 참인 경우, 종료 후 2초 안에 결과를 받지 못한 경우다. CSV 패턴만 보고 슬롯 수를 늘리기 전에 각 경우를 따로 세었다.

## 가설과 대안

1920×1080 Release 120프레임을 같은 장면에서 다시 실행했다. 고정 16슬롯 결과는 시작 거부 17, 정상 해석 103, disjoint 0, 미해석 0이었다. 누락은 GPU 주파수 변화나 종료 timeout이 아니라 query 풀 포화에서 생겼다.

`GetData`가 끝날 때까지 프레임마다 기다리면 누락은 없어지지만 CPU 프레임 시간에 대기가 섞인다. 누락 행을 버리고 나머지만 요약하면 측정이 빠른 프레임 쪽으로 치우칠 수 있다. 슬롯을 32나 64로 늘리는 방법도 현재 PC에서만 충분하다는 보장이 없다.

## 구현

`GpuFrameTimer`가 고정 배열을 갖는 대신 실행 시 슬롯 수를 받도록 바꿨다. benchmark는 측정 프레임 수와 같은 수의 슬롯을 넘긴다. 아직 결과가 오지 않아도 이번 실행에서 필요한 다른 프레임의 query를 시작할 수 있다. 과도한 객체 생성을 막기 위해 한 실행의 측정 구간은 10,000프레임까지 허용한다.

회귀 테스트는 WARP에서 query 20개를 해석하지 않은 채 연속 제출한다. 16개 고정 풀이면 17번째부터 실패하고, 구성한 수만큼 슬롯을 만들면 20개가 모두 시작된다.

## 검증

수정 뒤 같은 1920×1080 120프레임 진단은 시작 거부 0, 정상 해석 120, disjoint 0, 미해석 0이었다. fix commit `69b7a53`에서 회귀 테스트를 포함한 CTest 73건이 통과했다.

RTX 경로에서 1920×1080 3프레임을 별도로 실행하고 마지막 back buffer를 readback했다. clear 색 이외의 픽셀이 확인돼 스트레스 장면 렌더 검증도 통과했다.

깨끗한 commit `80988ef71f21430fc6baabea7b3d5cb4beae71f0`에서 전체 기준선을 다시 실행했다. GPU 값 600개가 모두 채워졌고 CPU와 GPU에서 16.7ms를 넘은 프레임은 없었다.

| 항목 | P50 | P95 | P99 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| CPU frame | 2.0068ms | 3.9227ms | 4.6404ms | 5.5797ms |
| GPU forward | 2.085888ms | 3.885056ms | 4.455424ms | 4.978688ms |

매 프레임 2,240 draw calls, 944,480 triangles, 1,124 objects였다. 성공 원본은 [20260823-033736 실행](../benchmarks/forward-baseline/20260823-033736-80988ef7-seed20260823/RESULT.md)에, 첫 실패 원본은 [20260823-032931 실행](../benchmarks/forward-baseline/20260823-032931-36163138-seed20260823/FAILED.md)에 남겼다.

## 남은 한계

이 수치는 렌더링 부하 장면만 잰 것이다. 전투 로직, 네트워크, UI, 그림자와 투명 패스 비용은 없다. 정적 객체도 여러 종류의 실제 맵이 아니라 같은 prototype mesh를 반복했다.

working set은 측정 첫 프레임 182,026,240바이트에서 마지막 238,190,592바이트로 늘었다. 대부분 첫 60프레임에서 증가했고 마지막 100프레임 증가는 217,088바이트였다. 안정화 경향은 보였지만 600프레임만으로 누수가 없다고 결론내리지 않는다. 30분 반복 검증은 10주차 부하 시나리오에서 별도로 진행한다.

5주차 비교에서는 같은 commit 방식, seed, 카메라 경로와 해상도를 유지한다. 포워드 기준선 자체가 이미 16.7ms 이하여도 개선 사례를 만들기 위해 수치를 과장하지 않고, GPU 패스와 draw call 변화가 실제로 확인된 항목만 채택한다.
